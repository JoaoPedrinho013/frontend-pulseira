# Zelo — front-end

Site do **Zelo** (pt-BR): pulseira inteligente (ESP32 + GPS NEO-6M + MPU6050) que acompanha a localização de uma pessoa e detecta possíveis quedas, avisando um responsável. Projeto acadêmico (prova de conceito) da FATEC Praia Grande (DSM).

Stack: React 19 + Vite + TypeScript estrito + react-router-dom. CSS Modules + tokens. Sem UI kit, sem testes.
O back-end fica em outro repositório (`../backend-pulseira`: Java/Spring Boot + MongoDB). **Hoje o front não chama nenhuma API**: é só site institucional. Não altere o back-end a partir daqui.

## Comandos
- `npm run dev` (porta 5173) · `npm run build` (= `tsc -b && vite build`) · `npm run lint` (oxlint) · `npm run preview`
- **Deploy (GitHub Pages):** `.github/workflows/deploy.yml` (push em `main`, só para o dono do repo) roda `npm ci` + `npm run build`, copia `dist/index.html` → `dist/404.html` (fallback SPA) e publica. `vite.config.ts` usa `base: '/frontend-pulseira/'` **só no build** (`'/'` no dev). Não alterar workflow/`base` sem combinar. `vite preview` usa `base '/'`, então **não serve para testar o Pages**.

## Rotas (`src/router/routes.tsx`)
Dentro de `MainLayout` (header + footer): `/` Landing (só hero) · `/sobre` Sobre o projeto (âncoras `#como-funciona`, `#beneficios`) · `/sensores` · `/contato` · `/privacidade` · `/faq` (`?pagina=N`) · `*` `NotFoundPage` (404 — captura qualquer caminho não mapeado dentro do `MainLayout`; mostra a URL digitada e um botão para voltar à `/`).
Fora do `MainLayout` (standalone, sem header/footer do site): `/login`, `/cadastro` (`AuthLayout`) e as três dashboards com `DashboardLayout` — `/admin`, `/paciente` e `/responsavel`.
`ScrollToTop` (em `App.tsx`) rola ao topo a cada troca de rota e para `#hash` quando houver. O "Entrar" do Header/CTAs já leva a `/login`.
**Nenhuma dashboard tem guarda de rota**: `/admin`, `/paciente` e `/responsavel` são acessíveis direto pela URL, sem checar sessão/perfil (não há sessão real — ver Armadilhas). No login, o campo "E-mail ou CPF" é um atalho mockado (`destinoPorIdentificador` em `LoginFormSection.tsx`): `admin` → `/admin`, `paciente` → `/paciente`, `responsavel` → `/responsavel`; qualquer outro valor vai para `/`. Senha não é checada.

## Estrutura de `src/`
- `pages/<nome>/` uma página + `sections/` (só o que é específico dela). Páginas: about, contact, faq, landing, privacy, sensors. `pages/auth/login` e `pages/auth/cadastro` seguem o mesmo padrão (página fina + `sections/LoginFormSection`/`CadastroFormSection` com o formulário em si). `pages/admin`, `pages/paciente` e `pages/responsavel` idem: página fina (`AdminPage`/`PacientePage`/`ResponsavelPage`) + `sections/` com cada bloco (conexões, status/mapa, dados médicos, log). `pages/not-found/NotFoundPage` é a 404 (sem `sections/`, não precisou).
- `components/<kebab-case>/` componentes reutilizáveis (`X.tsx` + `X.module.css`). `layout/` (MainLayout, PageContainer), `auth-layout/` (`AuthLayout` — casca de login/cadastro), `dashboard-layout/` (`DashboardLayout` — casca de `/admin`, `/paciente` e `/responsavel`: topo com marca + badge (`badgeLabel`) + "Sair", conteúdo em `PageContainer`), `header/`, `footer/`, `form-field/` (`FormField`, `PasswordField`), `avatar/` (`Avatar`, aceita `size` opcional p/ usos compactos), `stat-card/` (`StatCard`, aceita `tone?: 'primary' | 'success' | 'alert'` p/ colorir o ícone), `distribution-bar/` (`DistributionBar` — mini gráfico de barra empilhada, CSS puro), `connection-card/` (`ConnectionCard` — card de pareamento genérico: form com código + botão quando desconectado, resumo + "Desconectar" quando conectado; usado só pra pulseira hoje), `patient-code-card/` (`PatientCodeCard` — card do lado do paciente que exibe/compartilha `codigoVinculo` em vez de pedir um código; reaproveita as classes de `ConnectionCard.module.css`), `checklist-field/` (`ChecklistField` — `<fieldset>` de checkboxes, ou radio com `multiple={false}`, pros formulários médicos), `informacoes-medicas-form/` (`InformacoesMedicasForm` — formulário editável do paciente), `informacoes-medicas-view/` (`InformacoesMedicasView` — mesmo dado, somente leitura, pro responsável), `location-map/` (`LocationMap` — mapa via iframe do OpenStreetMap), `monitoring-log/` (`MonitoringLog` — timeline do log de telemetria), `ui/` (Button, IconButton, LinkButton), `icons/` (todos os SVGs em `index.tsx`).
- `data/` conteúdo e listas tipadas, **fora do JSX** (nomes em pt-BR para conteúdo de domínio: `beneficios.ts`, `passos.ts`, `faq.ts`...; `siteConfig.ts`, `footerData.ts`, `authPanelFeatures.ts`, `usuariosMock.ts` — usuários fictícios do `/admin`; `opcoesMedicas.ts` — checklists de tipo sanguíneo/alergias/condições/medicamentos + `rotulosSelecionados()`; `pacienteMock.ts` — paciente/responsável/pulseira fictícios de `/paciente` e `/responsavel`, incluindo `codigoVinculo`; `telemetriaMock.ts` — gera o log de localização fictício via `gerarTelemetriaMock()`).
- `hooks/` `useTheme`, `usePageMeta`, `usePaginacao<T>`, `useActiveSection`. `utils/` `classNames`, `paginacao`, `scroll`, `mascaras` (`formatarCpf`, `formatarDataBr`), `tempo` (`tempoRelativo` — "há N minutos"), `idade` (`calcularIdade`). `types/` tipos compartilhados (`politica.ts`, `theme.ts`, `usuario.ts` — conta do `/admin`; `paciente.ts`, `responsavel.ts`, `pulseira.ts`, `telemetria.ts` — domínio de `/paciente`/`/responsavel`, espelhando `../backend-pulseira`). `context/` tema.
- `styles/` `tokens.css` (única fonte de cor/espaço/tipografia), `fonts.css`, `reset.css`, `global.css`.
- `assets/fonts` (SF Pro Display, woff2) e `assets/images` (`hardware/`, `team/`, fotos da pulseira — **não usadas** no login/cadastro/dashboards, ver Armadilhas).

## Convenções
- TypeScript estrito, **sem `any`**, sem `@ts-ignore`; props tipadas; componentes pequenos; componentes PascalCase, hooks `useX`.
- Conteúdo em `data/`, nunca hardcoded em JSX longo. Listas com `key` estável (id/texto único).
- **Cores só por tokens** (`var(--color-*)`). Nenhum hex fora de `styles/tokens.css`. Estados (hover/active) derivam da paleta.
- Tipografia só por tokens (`var(--font-size-*)`), que já estão **+30% sobre o valor base** (ex.: `--font-size-md` é `1.3rem`, não `1rem`) — ajuste pedido para o sistema inteiro. Não reintroduzir os valores base nem escalar de novo; `--space-*`/`--radius-*` não foram tocados (só fonte, não espaçamento).
- Tema claro/escuro: atributo `data-theme` no `<html>`, chave `zelo:theme` no localStorage; `index.html` aplica o tema antes do React (evita flash). Tokens do escuro sobrescrevem os mesmos nomes em `[data-theme='dark']`.
- Fonte **San Francisco (SF Pro Display)** local, `font-display: swap`. Não trocar.
- Acessibilidade: HTML semântico, headings em ordem, `alt` descritivo, foco visível, alvos ≥ 44px, `prefers-reduced-motion` respeitado, contraste WCAG AA.
- Imagens abaixo da dobra com `loading="lazy"` e `width/height`; a do topo não.
- Texto das dashboards (`/admin`, `/paciente`, `/responsavel`) é enxuto de propósito: frases curtas, linguagem simples (ex.: "saúde" em vez de "informações médicas", "Histórico" em vez de "Log de monitoramento"), sem repetir no corpo o que o título/ícone já diz. Pedido explícito do usuário pra ficar mais acessível a públicos diferentes — não reverter pra frases mais longas/formais ao editar essas telas.

## Armadilhas
- **Deploy sob subcaminho:** o Pages serve em `/frontend-pulseira/`. Por isso `BrowserRouter` usa `basename={import.meta.env.BASE_URL}` (`main.tsx`) e o logo usa `import.meta.env.BASE_URL` (`siteConfig.logoSrc`). Caminhos absolutos como `'/favicon.svg'` em JS quebram no Pages (sem isso o site abria em branco: `No routes matched`). Em dev `BASE_URL` é `/`. Em novos assets/links de JS, sempre use `BASE_URL`.
- `position: sticky` do Header exige que `html/body/#root` **não** tenham `height: 100%`/`overflow` (já removido do reset; não reintroduzir).
- Breakpoint do menu mobile está duplicado: `matchMedia('(min-width: 768px)')` em `Header.tsx` e `@media (max-width: 767px)` em `Header.module.css`. Mude os dois juntos.
- `zelo:theme` existe em dois lugares: script inline do `index.html` e `ThemeContext.tsx`.
- `footerData.ts` é a fonte única dos desenvolvedores (footer + `/contato`); Backend aparece primeiro (`backendCreators`/`otherCreators`).
- `politicaPrivacidade.ts`: texto entre `[COLCHETES]` vira placeholder destacado. Descreve o modelo de dados do back-end **atual** (só modelagem, sem controllers); revisar se o back-end mudar.
- `FaqListSection` só considera aberto o item da página atual; `usePaginacao` mantém a página em `?pagina=`.
- `ghost` (Button) e `--font-weight-regular` existem mas ainda não têm uso (mantidos de propósito).
- `AuthLayout`: o painel de marca (lado esquerdo em ≥900px) usa `background: var(--color-primary)` + `color: var(--color-primary-contrast)`, igual ao `CallToAction` — no tema escuro `--color-primary` fica claro de propósito (contraste), não é bug. Painel não tem mais foto da pulseira (removida a pedido; não reintroduzir imagem ali). Destaques do painel vêm de `data/authPanelFeatures.ts`.
- `AdminPage`: a lista de usuários é `useState(usuariosMock)` local — "excluir"/"desativar" só mudam o state em memória (confirmado via `window.confirm` antes de excluir). Dar F5 restaura os 10 usuários do mock. Não tem paginação/busca/filtro (lista pequena, não precisou ainda).
- Badges de status (`AdminUsersSection`, `ConnectionCard`) e o ícone do `SummaryCard` usam `color-success` como texto **sobre** `color-success-soft`, não o inverso — é o padrão já usado no projeto para "soft badge", não confundir com o par `--color-success`/`--color-success-contrast` (esse é p/ texto sobre `--color-success` sólido). O mesmo padrão vale pro alerta de queda (`color-alert` sobre `color-alert-soft`, em `MonitoringLog`/`StatCard`) — é o único lugar do projeto que usa a cor coral, de propósito.
- `PacientePage`/`ResponsavelPage`: `Usuario` (`types/usuario`, usado só no `/admin`) e `Paciente`/`Responsavel` (`types/paciente`, `types/responsavel`) são modelos **diferentes** — não confundir. `Usuario` é a linha da tabela de contas do admin; `Paciente`/`Responsavel` espelham `PessoaMonitorada`/`Cuidador` do back-end, com dados médicos/endereço.
- **Vínculo paciente↔responsável**: quem inicia é sempre o responsável. O paciente nunca digita um código pro lado do responsável — ele só vê/compartilha o próprio `codigoVinculo` (`PatientCodeCard`, no card "Responsável" do `/paciente`). O responsável digita esse código no card "Paciente" do `/responsavel` (`ConexaoPacienteSection`), clica em "Buscar paciente"; se bater com `pacienteMock.codigoVinculo` (comparação case-insensitive, só isso é validado — mock não tem usuários extras), aparece uma etapa de confirmação com `Avatar` + nome + idade + telefone + bairro/cidade antes de "Confirmar vínculo"; código errado mostra uma mensagem de erro inline (sem usar `--color-alert` — essa cor é só pra queda, ver Paleta). "Cancelar" volta pra etapa de busca.
- `PacientePage`: pulseira começa `desconectada` (pra testar o pareamento do zero), mas responsável já começa **conectado** (`responsavelMock`) — não tem como esse lado "conectar" mais, só "Desvincular" (que volta a mostrar o `codigoVinculo` pra compartilhar de novo). O card "Pulseira" controla se a seção "Seus dados agora" aparece — sem pulseira conectada, não tem telemetria pra mostrar. O formulário de dados médicos (`InformacoesMedicasForm`) fica sempre visível, independente da pulseira.
- `ResponsavelPage`: começa sem paciente conectado (`paciente: null`). Como as duas dashboards são abas/sessões independentes (sem back-end nem estado compartilhado), o vínculo confirmado aqui não reflete de volta no `/paciente` que você abrir depois — é só o estado local de cada página.
- `LocationMap`: iframe público do OpenStreetMap (`openstreetmap.org/export/embed.html`), sem chave de API nem dependência nova — mantém o "sem UI kit". Exige internet pra carregar o tile; se o projeto crescer, a escolha de um provedor de mapas definitivo (com SDK próprio) é uma decisão de produto em aberto.
- `telemetriaMock.ts`/`gerarTelemetriaMock()`: gera 24 registros (2h, a cada 5 min) com jitter aleatório de lat/long em torno de Praia Grande - SP; um registro fixo (índice 5) vem com `status: 'possivel_queda'` só pra sempre ter um alerta visível no log pra demonstração. Chamado dentro de `useMemo(() => ..., [])` — os números mudam a cada reload da página, mas não a cada re-render.

## Pendências reais (não remover)
- `data/faq.ts`: respostas em lorem ipsum (`// TODO: substituir pelas respostas reais`).
- `data/politicaPrivacidade.ts`: placeholders (controlador, e-mail, prazos de retenção, DPO etc.) + revisão jurídica.
- `LoginFormSection`/`CadastroFormSection`: formulários só fazem `navigate()` no submit (`/` e `/login`, respectivamente) — sem validação real, sem chamada de API, sem estado de erro/loading. "Lembrar de mim" e "Esqueceu sua senha?" são inertes (sem handler). Isso é esperado enquanto o front não integra com o back-end.
- `AdminPage`/`usuariosMock.ts`: tela 100% mockada — sem API, sem sessão/guarda de rota, sem paginação/busca. Quando o back-end expuser endpoints de usuários, trocar o mock por fetch real e adicionar proteção de rota (hoje qualquer um acessa `/admin` direto pela URL).
- `PacientePage`/`ResponsavelPage`: 100% mockadas, iguais ao `/admin` nesse sentido — sem API, sem sessão/guarda de rota, sem WebSocket/polling de verdade (o "tempo real" é só o registro mais recente do mock). Os tipos (`types/paciente.ts`, `types/responsavel.ts`, `types/pulseira.ts`, `types/telemetria.ts`) já espelham `PessoaMonitorada`/`Cuidador`/`Pulseira`/`Telemetria` do back-end pra facilitar a troca. Falta, quando o back-end tiver endpoints: busca real do paciente por `codigoVinculo` (hoje compara só contra o único mock) e persistência do vínculo entre as duas dashboards (hoje cada página tem seu próprio state, sem sincronização), geocodificação reversa de verdade pro bairro/cidade do log (hoje é uma lista fixa em `telemetriaMock.ts`), e atualização ao vivo (polling ou WebSocket) em vez do snapshot gerado uma vez por carregamento de página.
